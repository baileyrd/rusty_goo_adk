# capability-manifest.md — rusty_goo_adk (Rust port of google/adk-python)

This is the running source of truth for the migration, per the `rust-migration`
skill's boundary contract: **every row defaults to REQUIRED.** A row only
moves to `OUT-OF-SCOPE` with a written, user-attributed reason; a row only
moves to `DONE` with a linked PR and named parity test. Nothing is dropped by
omission. `scripts/check_manifest_coverage.sh` fails loudly if any row is
neither `DONE` nor `OUT-OF-SCOPE`.

Source repo inventoried: [google/adk-python](https://github.com/google/adk-python)
at the commit cloned 2026-08-21 (~206k lines, 28 top-level modules under
`src/google/adk/`). Inventory performed by 8 parallel read-only agents per
`src/google/adk/{module}/` groupings; full per-module notes are preserved in
this repo's development history (see the rust-migration skill's scratch
output for this run) and can be pulled back up if a row's evidence needs
expansion before it's worked.

## Phases

Capabilities are grouped into phases in rough dependency order — a phase is a
sequencing device for the roadmap, not a scope cut. All phases are in scope;
later phases just depend on earlier ones landing first (e.g. you need a
session backend before compaction has anything to compact). Work phases in
order; within a phase, order is up to whoever's picking up the next issue.

**Note on format**: this list is deliberately plain text, not a markdown
table — `check_manifest_coverage.sh` assumes exactly one pipe-table in the
whole file (the capability table far below) and locates its columns from
the *first* header row it sees; a second table here would be misread as
that first header and break the coverage check.

- **P1 — Core runtime primitives**: `platform/` (random/time/uuid/thread providers), `errors/`, `events/`
- **P2 — Agent core & context**: `agents/` base classes (`BaseAgent`, `Context`/`InvocationContext`/`ReadonlyContext`, `RunConfig`, `LiveRequestQueue`), `LlmAgent` core
- **P3 — Model layer core**: `models/` base (`BaseLlm`, `LlmRequest`/`LlmResponse`, `LLMRegistry`, `CacheMetadata`), native Gemini backend
- **P4 — LLM flow engine**: `flows/llm_flows/` (`BaseLlmFlow`, request/response processors, `functions.py`, audio/transcription), `planners/`
- **P5 — Sessions**: `sessions/` — all 4 backends, schemas, migration tooling
- **P6 — Memory & artifacts**: `memory/` (3 backends), `artifacts/` (3 backends)
- **P7 — Multi-agent & workflow**: `apps/` (incl. compaction), `workflow/` (graph engine), `agents/` subclasses (Sequential/Parallel/Loop/RemoteA2a/Managed/LangGraph), `plugins/`
- **P8 — Tools core & built-ins**: `tools/` core infra + standalone built-in tools, `skills/`, `code_executors/`
- **P9 — Auth & credentials**: `auth/` — full credential lifecycle
- **P10 — Additional model providers & labs**: `models/` (Anthropic, LiteLLM, Apigee, Gemma, Interactions API), `labs/` (OpenAI, Antigravity)
- **P11 — Evaluation & optimization**: `evaluation/`, `optimization/`
- **P12 — Telemetry & feature flags**: `telemetry/`, `features/`, `dependencies/`
- **P13 — CLI & servers**: `cli/` — commands, HTTP/RPC server (dev + prod), deploy pipelines
- **P14 — A2A protocol**: `a2a/`
- **P15 — Cloud integrations**: `integrations/` — all cloud-service integrations, Google API toolsets
- **P16 — Repo-wide / build & packaging**: pyproject.toml-equivalent (Cargo features), CI, docs-as-spec items
- **P17 — Deferred / standalone decisions**: bundled web UI (8.3MB Angular bundle), `examples/`

## RustyMill sibling-check methodology (step 1 pass)

A full `scan_platform_repos.sh` run per capability (~1000 rows) wasn't done in
this pass — infeasible at this granularity in one sitting. The **Existing
RustyMill impl** column below is populated only where a repo/purpose match is
obvious from `references/platform-directory.md`'s name/purpose heuristic
(confirm-don't-assume, per that file's own caveat); most rows are blank.
Step 3 re-runs `scan_platform_repos.sh` for real before hand-rolling each
capability when its issue is actually worked, so a blank cell here is not a
final answer — just an unconfirmed one. Candidates worth checking first based
on purpose overlap: `rusty_json` (serialization), `rusty_http`/`rusty_request`
(HTTP client), `rusty_url` (URL parsing), `rusty_tls` (TLS/mTLS), `rusty_db`
(session/DB backends), `rusty_provider` (LLM provider abstraction —
directly relevant to `models/`), `rusty_llama` (local LLM inference),
`rusty_search` (retrieval/search abstraction), `rusty_compactor` (token
compaction — directly relevant to `apps/compaction.py`), `rusty_wire` (binary
serialization), `rusty_tokio` (async runtime), `rusty_prime_agent` (Rust
rewrite of another agent daemon's session/worker core — check for reusable
runtime-loop patterns).
